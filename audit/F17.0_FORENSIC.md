# F17.0 — FORENSIC AUDIT: WHY PSY4 CANNOT LEARN

**HEAD:** `e3b7e21` (F16) · **Method:** Trace every arrow in the radio→composition pipeline.

## THE CRITICAL ANSWER

**"What did the radio teach us during the last 16/32/64 bars, and how did that knowledge change the next phrase?"**

**The system CANNOT answer this.** Here is the proof:

1. **What is observed:** occupancy (4 scalar values), spectralEnergy (1 scalar), bassFreq (1 scalar or undefined), confidence (1 scalar). Total: ~7 numbers per 200ms tick.

2. **What is stored:** bpmHistory, energyHistory, densityHistory, occupancyHistory (arrays of scalars, bounded to 32 entries). No pattern memory, no feature memory, no timbre memory.

3. **What is retrieved during composition:** `window.snapshot(bar)` returns `currentOccupancy`, `energyRising`, `bpmStable`. These are 3 boolean/scalar derivations. The composer uses `radio.currentOccupancy.lead > 0.6` to gate lead density. That is the ONLY radio-influenced composition decision.

4. **What changes in the next phrase:** lead density (multiplied by 0.5 if radio.lead > 0.6). Nothing else. The kick pattern, bass pattern, hat pattern, motif selection, and synthesis parameters are ALL independent of radio observations.

**Verdict: The radio influences exactly ONE scalar multiplier (lead density). It does not teach the system anything musical.**

## MUSICAL MEMORY AUDIT

### MusicalMemory (current)

**Stores:** `StoredMotif[]` — motifs generated by `generateMotif()` (random seed, not from radio).

**pickMotif scoring:**
```
score = m.reward * 0.4                    // reward from post-hoc evaluation
      + (barsSinceUse < 4 ? -0.3 : 0)    // anti-repetition
      + (barsSinceUse > 16 ? +0.1 : 0)   // callback bonus
      + noveltyBudget * 0.2              // transform bonus
      - usageCount * 0.02                // usage penalty
      - (rejected ? 0.5 : 0)             // rejection penalty
      + rng.next() * 0.05                // tiebreaker
```

**Problem:** All motifs come from the same `generateMotif()` function with random seeds. They are statistically identical material. The reward is `coherence*0.3 + densityFit*0.25 + 0.25 + novelty*0.2` — always ~0.55-0.75 regardless of output. So `m.reward * 0.4` is ~0.24 for all motifs. The selection is effectively random.

**Verdict: MusicalMemory stores motifs, but none of them are learned from radio. The "learning" is post-hoc reward bookkeeping that doesn't discriminate.**

### RadioMusicalWindow (current)

**Stores:** scalar histories (bpm, energy, density, occupancy) bounded to 32 entries.

**Problem:** No pattern memory. No feature extraction. No abstraction. The window stores "what was the average energy" not "what was the bass rhythm pattern."

## TRANSPORT CONTINUITY AUDIT

The user reports: "Between phrases / transitions the rhythm resets and PSY4 has to catch the radio again."

**Root cause investigation:**

MusicalTransport (`foundation/transport/MusicalTransport.ts`) is anchor-based:
- `beatTime = anchorTime + (beatIndex - anchorBeatIndex) * beatDuration`
- `observeBeat()` re-anchors when confidence is high
- `loseSource()` enters holdover (confidence decays, BPM holds)

**Does the transport reset at phrase/section boundaries?**

Let me trace `planBar()`:
- `barInPhrase = bar % 8` — phrase boundary at bar % 8 === 0
- `handleNewPhrase()` at barInPhrase === 0 — clears phraseMotifs, creates new motif
- Section changes at bar % 64 === 0, 8, 16, etc.

**Does handleNewPhrase touch the transport?** No — it only manages motif memory.

**Does the scheduler reset at phrase boundaries?** No — it reads `transport.snapshot()` every 25ms and schedules 16th notes continuously.

**So where does the "reset" come from?**

The transport itself is continuous. But the COMPOSITION resets:
- `phraseMotifs.clear()` at barInPhrase === 0 — motif memory wiped per phrase
- `phraseNotes = []` — phrase evaluation history wiped
- New motif created — may have different register/contour

The user perceives a "reset" because the musical material changes abruptly at phrase boundaries, not because the transport resets. The transport is fine.

**BUT:** if the radio PLL re-anchors at a phrase boundary (because confidence happens to peak there), the beat phase could jump. Let me check `observeBeat`:

MusicalTransport.observeBeat re-anchors when:
- confidence > lockThreshold (0.5)
- the observation is within phase tolerance

If the radio signal was degraded during a phrase transition and then recovered, the re-anchor could cause a phase jump. This is the "catch the radio again" problem.

**Verdict: Transport is continuous in code, but radio re-acquisition after signal degradation can cause phase jumps. The composition also resets motif memory at phrase boundaries, creating a musical discontinuity.**

## ARCHITECTURAL BLOCKERS

### Blocker 1: No Musical Observation Model
The system observes raw scalars (RMS, occupancy) but not musical features (pitch-class histogram, interval contour, rhythm pattern, spectral centroid). Without musical observations, there is nothing to learn.

### Blocker 2: No Musical Memory
MusicalMemory stores generated motifs, not learned features. There is no `MusicalObservation`, `BassGrammar`, `RhythmGrammar`, or `TimbreProfile` type. The memory cannot answer "what did we hear?"

### Blocker 3: No Feature→Composition Bridge
The composer (MusicalSession) reads `ctx.snapshot()` and `window.snapshot()`, both of which are scalar derivations. There is no path from "learned bass grammar" to `generateBass()`.

### Blocker 4: Circular BPM Observation
`psyLive.detect()` passes `transportSnap.bpm` (the engine's own BPM) to `session.observeRadio({bpm: transportSnap.bpm})`. The session observes the engine's BPM, not the radio's detected BPM. This means the composer doesn't know what tempo the radio is actually playing.

### Blocker 5: No Timbre Analysis
The FFT data is available (`radioFreqBuf`) but only used for band-energy occupancy. No spectral centroid, flatness, rolloff, or flux is computed. No timbre profile exists.

### Blocker 6: Motif Memory is Not Learned
`generateMotif()` creates motifs from random seeds. `pickMotif` selects from these. None of the motifs are derived from radio observations. The "learning" is reward bookkeeping on randomly generated material.

## F17 IMPLEMENTATION PLAN

### F17.1 — Fix Transport Phase Continuity
- Ensure `observeBeat()` smooths phase corrections (no jumps)
- Ensure phrase/section boundaries don't trigger re-anchoring
- Add phase error to transport snapshot for monitoring
- Test: 256-bar run with simulated radio, measure phase error and relock count

### F17.2 — Build MusicalObservation
Create `foundation/music/MusicalObservation.ts`:
- `RadioMusicalFeatures` interface: tempo, harmony, rhythm, melody, timbre features
- `MusicalObservationExtractor` class: takes radioSnap + frequency data, extracts features
- Features: pitchClassHistogram, intervalHistogram, bassRhythmPattern, hatDensity, syncopation, spectralCentroid, spectralFlatness, spectralRolloff, energyEnvelope, velocityDistribution
- Stored per-phrase (not per-tick)

### F17.3 — Build Real MusicalMemory
Extend `MusicalMemory` with:
- `learnedBassGrammar`: interval transitions, rhythmic positions, approach tones
- `learnedRhythmGrammar`: kick onset patterns, hat density patterns, syncopation
- `learnedTimbreProfile`: spectral centroid, flatness, brightness per voice
- `learnedMelodicGrammar`: contour patterns, interval preferences, phrase length
- Retrieval: `getBassGrammarForContext(section, energy, key)`, etc.
- Persistence: high-confidence profiles stored for reuse

### F17.4 — Wire Learned Grammar into Composition
- `generateBass`: if learned bass grammar exists, generate from learned interval transitions instead of hardcoded beatDegrees
- `generateKick`: if learned rhythm grammar exists, generate from learned onset patterns
- `generateHats`: if learned hat density exists, use learned syncopation
- Fallback: current hardcoded grammars (when no learning exists)

### F17.5 — Wire Learned Melodic Grammar
- `generateLead`: if learned melodic grammar exists, generate new motifs from learned contour/interval preferences
- Replace pure-random `generateMotif` with learned-grammar-based generation when memory is available

### F17.6 — Timbre → Synthesis Mapping
- `TimbreProfile` → synth parameter mapping (oscillator type, filter cutoff, Q, saturation amount, envelope shape)
- When radio teaches "dark bass with strong sub", map to: bassWave=sine, bassCut=lower, saturation=higher
- Apply to voices dynamically

### F17.7 — Shared Knowledge Contracts
- Define `SoundProfile`, `MusicalPattern`, `BassGrammar`, `TimbreProfile` as shared types
- Persist to localStorage (high-confidence profiles only)
- Design for cross-application reuse

### F17.8 — Phrase Continuity State
- `PhraseState` carries forward: previousBassState, previousLeadState, previousMotif, harmonicState, energyState, learnedFeatures
- `handleNewPhrase` no longer wipes everything — carries forward learned grammars and motif state

### F17.9 — Self-Evaluation + Reward
- After each phrase, evaluate: did the learned grammar produce coherent music?
- Reward: coherence (scale fit), novelty (not copying radio), identity (psy4 character)
- Update learned grammar confidence based on reward

### F17.10 — A/B Reality Test
- Session A: play radio for 128 bars, capture learned features, continue
- Session B: same seed, no radio learning
- Compare: bass vocabulary, rhythmic vocabulary, melodic contour, timbre
- Must measurably differ
