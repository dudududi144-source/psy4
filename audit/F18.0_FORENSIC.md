## THE 30 QUESTIONS — ANSWERED WITH CODE EVIDENCE

### 1. What exact radio features are currently captured?
**Answer:** `psyLive.ts:1043-1054` passes to `observeRadioTick`:
- `audioTime` (AudioContext.currentTime)
- `radioBpm` (from `radioSnap.beat?.estimatedBpm`)
- `energy` (spectralEnergy scalar)
- `occupancy` (4 scalars: kick/bass/lead/hats)
- `bassFreq` (single Hz value or null)
- `pitchClass` (0-11 or null)
- `pitchConfidence` (0-1)
- `freqData` (Uint8Array — raw FFT, 256 bins)
- `sampleRate`, `fftSize`

**Then `MusicalObservation.ts:extractSpectralFeatures()` derives from freqData:**
- spectralCentroid (brightness)
- spectralFlatness (noisiness)
- spectralRolloff (85th percentile)
- lowEnergy, midEnergy, highEnergy (band averages)

### 2. Which features survive into MusicalSession?
**Answer:** All of the above reach `MusicalObservationExtractor.observe()` as `RadioTickFeatures`. They are stored in a bounded array (max 200 ticks ≈ 40 seconds).

### 3. Which features are discarded?
**Answer:** At `extractPhraseFeatures()`:
- **Pitch contour** — individual pitch observations are aggregated into a histogram, but the SEQUENCE is lost. No interval transitions between specific notes.
- **Beat onset times** — only `kickOnsetPattern` (16-step average) survives. Individual onset timestamps discarded.
- **Velocity/accent information** — never captured.
- **Stereo information** — never captured.
- **Transient character** — never captured.
- **Harmonic rhythm** — never captured.

At `GrammarBuilder`:
- The `BassGrammar.intervalTransitions` matrix is built from the pitch-class histogram, NOT from actual note-to-note transitions. It's a statistical approximation, not a real Markov model.

### 4. How are observations aligned to musical time?
**Answer:** They're NOT aligned to musical time. Observations are collected at 200ms intervals (detect tick) and aggregated per-phrase by counting ticks. There is no beat-synchronous alignment. A phrase is assumed to be 8 bars, and ticks are divided proportionally — but if the BPM drifts, the tick-to-bar mapping becomes inaccurate.

### 5. What happens at phrase boundaries?
**Answer:** `MusicalSession.planBar()` at `barInPhrase === 0`:
1. `extractPhraseLearning(phraseIndex - 1, bar - 8, 8)` — feeds accumulated ticks to GrammarBuilder
2. `phraseMotifs.clear()` — per-bar motif cache wiped
3. `phraseNotes = []` — phrase evaluation history wiped
4. `handleNewPhrase()` — creates or transforms the current motif

**Problem:** `handleNewPhrase()` creates a NEW motif via `generateMotif()` (random seed) if the motif group is empty. This is a musical reset — the new motif has no relationship to the previous phrase's motif unless it's a transform.

### 6. What happens at section boundaries?
**Answer:** Section changes at `bar % 64` boundaries. The only effect:
- `calculateLeadDensity` returns a different density (e.g., INTRO=0.2, CLIMAX=0.7)
- `generateBass` uses different `beatDegrees` (e.g., INTRO=[0,0,0,0], CLIMAX=[0,4,2,7])
- `generateKick` selects from a different grammar set (base vs climax)

**No reset of transport, memory, or learned grammars.** This is correct.

### 7. What happens when radio BPM changes?
**Answer:** `MusicalTransport.observeBeat()` smooths tempo: `this.bpm += (observedBpm - this.bpm) * 0.08`. No reset. The epoch only increments if phase error exceeds threshold at a bar boundary (30% correction). This is correct.

### 8. What happens when radio loses signal?
**Answer:** `RadioObservationLayer` transitions to LOST after 2 seconds of no signal. `psyLive.detect()` stops calling `observeRadioTick`. Transport enters holdover (`loseSource()`). Learned grammars are preserved. No reset.

### 9. Does composition reset at boundaries?
**Answer:** PARTIALLY:
- **Phrase boundary:** `phraseMotifs.clear()` + new motif created. This IS a partial reset — the motif material changes.
- **Section boundary:** No reset. Only density/pattern parameters change.
- **Transport:** No reset. Continuous.

### 10. Does learned knowledge survive boundaries?
**Answer:** YES. `GrammarBuilder` accumulates across phrases. `phraseMotifs.clear()` only clears the per-bar cache, not the grammar. This is correct.

### 11. Does lead actually consume learned melodic information?
**Answer:** **NO.** `generateLead()` (line 558+) uses `motif.notes` from `MusicalMemory`. The motif is created by `generateMotif()` (random seed) or `transformMotif()` (transpose/invert/fragment/retrograde). `getLearnedMelodicGrammar()` exists but is **never called** by `generateLead()`. The learned melodic grammar is dead code.

### 12. Does bass consume learned harmonic information?
**Answer:** **YES.** `generateBass()` checks `getLearnedBassGrammar()` and calls `generateLearnedBass()` when confidence > 0.25. This is the only working learning path.

### 13. Does rhythm consume learned rhythm information?
**Answer:** **NO.** `getLearnedRhythmGrammar()` exists but is **never called** by `generateKick()` or `generateHats()`. The learned rhythm grammar is dead code.

### 14. Does synthesis consume learned timbre information?
**Answer:** **NO.** `getLearnedTimbreProfile()` exists but is **never called** by the voice functions (`kick()`, `bass()`, `lead()`, `hat()`). The learned timbre profile (including `synthParams`) is dead code.

### 15. Does the system distinguish observed/abstracted/generated material?
**Answer:** **NO.** There is no explicit separation. `MusicalMemory` stores generated motifs alongside learned motifs. There is no `MaterialRecord` type that distinguishes source.

### 16-20. Can the system learn scale/key/intervals/rhythm/contour/phrase structure?
**Answer:**
- **Scale/key:** PARTIALLY — `pitchClassHistogram` is extracted, `dominantPitchClass` computed. But `MusicalContext.rootPc` is set from a single `bassFreq`, not from the histogram. No hysteresis.
- **Intervals:** NO — interval transitions are approximated from the histogram, not from actual note sequences.
- **Rhythm:** PARTIALLY — `kickOnsetPattern` (16-step average) is extracted. But not used by the composer.
- **Contour:** PARTIALLY — `melodicContour` (direction changes) is extracted. But not used.
- **Phrase structure:** NO — phrase length is hardcoded to 8 bars.

### 21. Can it learn bass movement independently from exact notes?
**Answer:** **YES.** `BassGrammar.intervalTransitions` is a 12×12 probability matrix, not note storage. `generateLearnedBass()` samples from this distribution. It does not copy notes.

### 22. Can it learn sound/timbre characteristics?
**Answer:** **YES** (extracted) but **NO** (not applied). `TimbreProfile` with `synthParams` is built but never consumed by synthesis.

### 23. Can it create new material from those abstractions?
**Answer:** **YES for bass. NO for lead, rhythm, timbre.** Only `generateLearnedBass()` creates from abstractions.

### 24. Can it evaluate whether generated material fits the radio?
**Answer:** **NO.** `evaluatePhrase()` computes `reward = coherence*0.3 + densityFit*0.25 + 0.25 + novelty*0.2`. This is a post-hoc formula that doesn't compare against radio features. No candidate scoring.

### 25. Can evaluation influence future generation?
**Answer:** **PARTIALLY.** `pickMotif()` uses `m.reward * 0.4` in scoring. But since all motifs have reward ~0.6, the effect is negligible. No feedback loop to grammar confidence.

### 26. Does knowledge persist after the current session?
**Answer:** **NO.** `GrammarBuilder` is in-memory only. No serialization to localStorage. `reset()` wipes everything.

### 27. Can learned knowledge be reused by another PSY application?
**Answer:** **NO.** No persistence contracts. No shared data format. The types exist but are not serialized.

### 28. Is there any accidental copying of observed sequences?
**Answer:** **NO.** The system never stores note sequences from radio. `MusicalObservationExtractor` stores only aggregated features (histograms, averages, patterns). `generateLearnedBass()` samples from probability distributions.

### 29. Is there any hidden hardcoded generator overriding learned material?
**Answer:** **YES.** `generateLead()` always uses the hardcoded motif system. `generateKick()` always uses `KICK_GRAMMARS`. `generateHats()` always uses hardcoded style patterns. These override any learned material because the learned grammars are never consulted.

### 30. Is there more than one musical authority?
**Answer:** **NO.** `MusicalSession.planBar()` is the single composer. No parallel composer exists. The problem is not multiple authorities — it's that the single authority doesn't use the learned knowledge.

## ROOT CAUSE OF "LOSING THE GROOVE"

The user reports the engine "loses the groove every few bars and tries to catch it again." Based on the forensic trace:

**The transport is NOT the problem.** It has smooth re-anchoring (30% correction at bar boundaries) and continuous phase tracking.

**The problem is the COMPOSITION resetting at phrase boundaries:**
1. `phraseMotifs.clear()` at `barInPhrase === 0` — wipes the per-bar motif cache
2. `handleNewPhrase()` may create a NEW motif via `generateMotif()` (random seed) — the new motif has no melodic relationship to the previous phrase
3. The lead generator uses this new random motif — the melody "jumps" to unrelated material
4. The bass grammar switches between learned (when confidence is high) and hardcoded (when it's not) — creating inconsistency

**The fix:** Build a `MusicalContinuityState` that carries forward:
- Previous motif (for development, not replacement)
- Harmonic context (key/scale with hysteresis)
- Learned grammars (already preserved)
- Energy/tension trajectory
- Previous phrase's bass/lead state
